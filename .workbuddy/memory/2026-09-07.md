## 修复：双语字幕文字重叠（XMBOX / fongmi TV 播放器）

- 现象：同时显示两条字幕（双语/双轨）时，文字叠在同一位置。
- 根因：media3 `SubtitleView` 是 `final` 不能继承；多条 cue 都定位在底部默认位置 → 重叠。
- 方案：`Player.Listener.onCues(CueGroup)` 拦截，把「同一定位（line/position 等相同）」的多条可合并 cue 合并为一条多行文本（用 `\n` 连接，保留 span），由 StaticLayout 自动上下分行；单条字幕 size<2 直接透传，行为不变。
- 新增：`app/src/main/java/com/fongmi/android/tv/player/exo/CueMerger.java`
- 改动：`ExoUtil.setSubtitleView(PlayerView)` 末尾调用 `CueMerger.attach(exo)`；`ExoPlayerEngine.createExoPlayer()` 在 `view.setPlayer` 后调 `ExoUtil.setSubtitleView(view)`（重建播放器也自动重新绑定）。
- 自测：`gradlew :app:compileMobileArm64_v8aDebugJavaWithJavac` 通过。
- 注意：MPV 引擎走自己的字幕渲染，本修复只覆盖 Exo 路径（默认引擎）。字幕若用 `\pos` 精确定位则不被合并（属字幕组有意排版）。

## 修复：历史记录不更新 / 每次从第一集看起（Bug 1）

- 现象：播放过的视频在历史记录页不显示、记录停滞；下次进入该剧总是从第一集/从头开始（续播失效）。
- 根因：`History.update()`（无参，每 1s 由 Clock→onTimeChanged→App.execute 触发）调用 `merge(find(), false)`。`find()` 返回同一剧名(vodName)下**所有集**记录；`merge` 里仅「当前集 key 相同」被 `continue` 跳过，其余每一集都走到 `item.delete()` → **看一集就把同剧其它集的历史全删了**。结果：历史页记录被持续删除而"停滞/不显示"；重进该剧时对应集记录已被删→只能从头（第一集）看。
- 改动：`app/src/main/java/com/fongmi/android/tv/bean/History.java:279` 的 `update()`：去掉 `merge(find(), false)`，改为遍历 `find()` 仅当 key 相同则 `checkParam(item)`（继承 opening/ending/speed），随后 `save()`，不再删除任何记录。`update(int cid)`（切换 cid 迁移逻辑，走 `merge(items, true)` 强删）保持原样未动。
- 续播链路：`checkHistory()` 用 `History.find(getHistoryKey())`（`cid+key` 精确查）→ 找得到对应集已存 position；修复后该集记录不再被删，续播恢复。
- 自测：compileMobile/TabletArm64_v8aDebugJavaWithJavac BUILD SUCCESSFUL。运行时需老陈确认：① 历史页能看到刚看的集且不再消失；② 重进该剧能续播。
- 老陈原话：想加 StrictMode 抓 Room 主线程（"可以的"），但被这俩 bug 打断；bug 修完后可回头做。

## 优化（安全项）：线程池无上限 → 有界可复用

- 老陈在优化清单里选了「先做安全的」：线程池复用 + Room 去 allowMainThreadQueries。
- **线程池（已改）**：全项目 2 处 `Executors.newCachedThreadPool()`（无上限，线程爆炸/OOM 风险）——
  - `player/ParseJob.java:49` 的 `infinite`（`for (Parse item : json) infinite.execute(...)`，item 多就无限开线程）→ `newFixedThreadPool(4)`。
  - `player/danmaku/DanPlayer.java:32` 的 `executor`（7 处 `execute` 短任务）→ `newFixedThreadPool(4)`。
  - 保持实例内池不改共享池：ParseJob 清理时会 `infinite.shutdownNow()`，共享池会被整个关掉。
  - 其余 `newFixedThreadPool(n)`（Source/DownloadService/M3U8*/ViewModel 等）本身有界且多数会 shutdown，未动——改并发度会影响加载时序，属非安全项。
- 自测：`:app:compileMobileArm64_v8aDebugJavaWithJavac` + `:app:compileTabletArm64_v8aDebugJavaWithJavac` 均 BUILD SUCCESSFUL（21s/56 tasks）。
- **Room（没改，原建议不成立）**：`AppDatabase.java:109` 的 `allowMainThreadQueries()` 不能删。全项目有几十处 `AppDatabase.get().getXxxDao().find/insert/...` 直接散在 bean 类（Site/Keep/Config/History/Live/Device/Track/Download/Backup/WebDAVHistorySync），多为 UI/主线程同步 getter 调用。删了会运行时抛 "Cannot access database on the main thread" 直接崩——必须先把所有主线程调用迁移到后台（大改），属非安全项，已向老陈说明并建议留待后续专项。
- **已产出迁移清单**：`docs/room-main-thread-migration.md`。精确统计 64 处 DAO 调用点（另 1 处 clearAllTables），按文件分布：Config 16、Keep 10、Backup 10、History 8、Download 6、WebDAV 4、Track 3、Device 3、Site 2、Live 2。已核实的主线程证据：VodConfig:126,380 / LiveConfig:96,305 / WallConfig:51,67 的 Config.vod()/live()/wall() 属**启动路径（P0，删开关＝开屏即崩）**；SettingFragment:479,494、KeepActivity:65、ConfigDialog:195,207,219、SyncDialog:70,77,78 属 UI 直调（P1）。Players:205 的 Track.find() 线程需实测确认。推荐迁移顺序（不能反）：先 StrictMode 抓真实调用栈 → 加异步版(LiveData/Executor) → 逐个改 UI → 最后才删开关。
