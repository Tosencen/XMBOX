# 2026-11-18

## 修复 3.1.9 启动/收藏崩溃 + 出 3.2.0 包

### 根因：Room 迁移漏列
- `Migrations.MIGRATION_33_34` 里 `CREATE TABLE Download` 只有 11 列，漏了 `statusInt`，而实体 `bean/Download` 有 12 列。
- 从 v33 数据库升级上来的设备在 `onUpgrade` 校验时抛 `IllegalStateException: Migration didn't properly handle: Download`，事务回滚 → 每次启动/首次触库都崩。
- 电视直播长按收藏也是同一根因：`Keep.exist()` 是直播流程里较早的一次触库，迁移失败直接抛出。

### 改动
- `db/Migrations.java`：抽出 `DOWNLOAD_DDL`（与 35.json 完全一致）；`ensureDownload()` 按 `PRAGMA table_info` 判断表/列，缺表建表、缺列则 Temp 表重建并搬数据（statusInt 补 0）；33→34 与新增的 34→35 都走它。
- `db/AppDatabase.java`：`VERSION` 34 → 35，注册 `MIGRATION_34_35`（顺带刷新 room 身份校验值，修"schema 未升版本"的情况）。
- `LiveActivity`（leanback/mobile/tablet 三端）：`onLongClick` 全包 try/catch；收藏状态优先查库、失败回退内存判断；`addKeep/delKeep` 的异步写库也各自 try/catch；`getKeep()` 加空/越界保护。收藏不再能把 App 打崩。
- 版本号 3.1.9(319) → 3.2.0(320)；`app/schemas/.../35.json` 已生成。
- 产出 `dist/3.2.0/`：mobile/leanback × arm64_v8a/armeabi_v7a 四个 release 包。

### 验证
- 三个 flavor `compile*JavaWithJavac` 通过；4 个 release 包 `assemble*` 通过。
- 用 sqlite3 跑了一遍"11 列旧表 → 重建"SQL，结果 schema 与 Room 期望完全一致，数据保留。

### 备注
- 用户说的"tv版也可以搜索"是笔误，实际指 TV 版长按收藏，不是搜索功能，暂不开发频道搜索。

## 追加：TV 端长按 OK 冲突
- `CustomKeyDownLive.check()` 里 `isLongPress && isEnter` → `onMenu()`（弹底部控制栏），会把频道列表项的长按收藏抢走。
- leanback `LiveActivity.dispatchKeyEvent` 增加 `isChannelLongPress()` 判定：频道列表有焦点且可见时长按 OK 不再走 `mKeyDown`，交给列表项自己处理（收藏）。

## 真机（Android 16 arm64 模拟器）测试结论
- 复现：把 DB 造成 v33（无 Download 表）→ 旧 3.1.7 启动即 `Migration didn't properly handle: Download`，栈与用户上报一致（HomeActivity:119 → Config.wall → ConfigDao.findOne）。
- 3.2.0：v33 库 → 升级到 35，Download 12 列齐全，Config 数据保留；v34 + 11 列 Download（含一条记录）→ 表重建补齐 statusInt，记录保留（statusInt 补 0）。
- 手机版：长按频道 "Added" + Keep 表写入 `CCTV2|1|...`，再长按 "Removed" + 记录删除，全程无 FATAL。
- TV 版：装 release 包可正常启动；仅系统 16KB page-size 提示（历史遗留 .so 对齐问题，与本次无关）。
