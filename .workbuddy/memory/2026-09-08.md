## 回归 #2 修复 + 最终 StrictMode 复测（本会话收尾）

- **回归 #2 根因**：上轮把 `initConfig` 异步化后，`VodFragment.initView`（早于异步 config 加载完成）调用 `VodConfig.get().getConfig()`，因 config 仍 null，fallback 到 `Config.vod()` 触发 `ConfigDao_Impl.findOne` 主线程读。StrictMode 结构化分析确认 3 条 `ConfigDao_Impl.findOne` 违规，栈为 `VodFragment.initStartupState(127)/checkEmptySource(240)/setLogo(535)` → `VodConfig.getConfig()(396)`。
- **修复**：让 `VodConfig/LiveConfig/WallConfig.getConfig()` 线程感知——`config != null` 直接返回；主线程且未加载时返回 `null`（不回退 Room 读）；后台线程（initConfig / SettingFragment）保留 `Config.vod()/live()/wall()` 懒加载。三文件各加 `import android.os.Looper;`。同时给 `VodFragment.setLogo()`（mobile/tablet 两份，line 534）加 `config == null` 守卫（`getConfig()` 为 null 时直接 return）。`initStartupState/checkEmptySource` 本就 try-catch 处理 null，配置加载完成后由 `onRefreshEvent(CONFIG)`→`setLogo()` 与 `onStateEvent(EMPTY)`→`checkEmptySource()` 重新刷新 UI，流程正确无 NPE。
- **复测结果（mobile arm64_v8a debug，emulator-5554，冷启→History→Keep）**：
  - Room/DAO/SQLite 主线程违规：**0 条**（回归 #2 与启动路径全部清零）。
  - SharedPreferences 磁盘读：3 条，均为 `App.onCreate→Setting.getProxy→Setting.getStr`（读代理偏好），非 Room、无害、与去开关无关。
  - 其他文件 I/O：0 条（确认 `backupDatabase` 后台化消除了启动 ~4s 主线程卡顿）。
- **结论**：可 runtime 触发的三条路径（启动 / History / Keep / VodFragment）StrictMode 主线程 Room 读已归零。`allowMainThreadQueries()` 仍保留——残留站点（VideoActivity.checkHistory、leanback getHistory、SyncDialog、CastDialog、HistoryAdapter、Backup、Download、leanback SettingActivity）均在本无视频源的 build 下无法 runtime 验证，盲改风险高，留待专项。

## 【收尾】静态核验盲区补齐 + `allowMainThreadQueries()` 已移除（完成）

**关键教训（重要，以后别再踩）**：此前几轮只用 grep 匹配 `ClassName.method()` 静态调用做核验，**漏掉了 `item.save()/.delete()/.update()` 这类实例方法里的 DAO 访问**。正确核验方式：先 grep `AppDatabase.get()` 拿到全部真实 Room 访问点（都在 bean 的静态/实例方法里），再反查每个调用方是否在 `App.execute` 内。据此新发现并迁移 13 类主线程残留（绝大多数在 UI 点击/删除回调）：
- 写：`ConfigAdapter.remove` 的 `item.delete()`；`SiteDialog`(m/t) 与 `SiteAdapter`(leanback) 的 `item.save()`；`LiveDialog`(m/t/l) 的 `item.save()`；`TrackDialog`(main) 的 `item.save()`；`ReceiveDialog`(m) 的 `history.update()`；`KeepActivity/HistoryActivity/HomeActivity(leanback).onItemDelete` 的 `item.delete()`；`DownloadActivity`(m) 的 `item.delete()`；`LiveActivity.addKeep`(m/t/l) 的 `keep.save()`。
- 读：`ConfigAdapter.addAll` 的 `Config.getAll(type)`（改异步后 `HistoryDialog` 调用改为先 `setAdapter` 再 `addAll`）；`CastDialog.getDevice`(m/t) 的 `Device.getAll()`。
- 澄清为非 DB（无需改）：`LiveActivity.getKeep()` 返回内存 Group、`TrackDialog.getTrack()` 由 ExoPlayer 轨道内存构建、`History.merge()` 只在 `update()` 内（主线程路径仅 ReceiveDialog）。

**异步化统一模式**：UI 点击/删除回调里的库写用 `App.execute(item::save)` / `App.execute(item::delete)`（fire-and-forget，UI 立即更新内存态）；库读用 `App.execute(读) → App.post(填 UI)`。链式写法 `item.setXxx(v).save()` 一律拆成「主线程 setXxx + 后台 save」。

**结果**：三 flavor `assemble*Arm64_v8aDebug` BUILD SUCCESSFUL；emulator-5554 实测 Room/DAO/SQLite 主线程违规 = 0（仅 3 条良性 SharedPreferences 读）。
**已移除** `app/src/main/java/com/fongmi/android/tv/db/AppDatabase.java` 的 `allowMainThreadQueries()`；重新编译 + 重装复测：无 `IllegalStateException: Cannot access database on the main thread`，无崩溃，冷启/History/Keep 均正常。
**遗留风险**：本 build 仍无视频源，Players / Sync / Cast / VideoActivity / ConfigDialog 等路径只经编译 + 代码评审，未 runtime 覆盖；建议配源后再复测一轮。
**同时废弃上文「仍悬置、未迁移」一节**：VideoActivity(checkHistory/Keep.find)、SyncDialog.history()/keep()、CastDialog body 等均已在后续轮次完成迁移或经核实本就在 `App.execute` 内。
